# Product Foundry Context

The pasted strategy context changes the product framing in an important way. Software Factory is not primarily a dashboard for AI telemetry. It is the operating system for a one-person software company: the founder makes strategic decisions, AI performs bounded work, repositories remain the source of truth, and the system preserves institutional memory and trust evidence.

## Principles adopted

The factory must cause the full lifecycle to get done rather than pretend that one person can personally master every specialty. The system therefore needs functional machines for research, product, design, engineering, AI, data, security, DevOps, quality, operations, sales, support, administration, and knowledge. These machines can begin as structured artifacts and deterministic tools before they become autonomous agents.

The lifecycle is modeled as a sequence of governed stages: discover, validate, model, design, architect, build, test, secure, observe, deploy, onboard, measure, learn, improve, and scale. The controlled repository-to-delivery loop implements the first operational slice of this model by connecting product brief, implementation plan, repository branch, modification, verification, preview, and evidence.

The trust layer is first-class. Security, audit, testing, observability, recovery, and human approval are not afterthoughts around an AI-generated product. They are the mechanism that turns generated software into software that can be trusted. Autonomy is proportional to reversibility: low-risk file changes in an approved workspace can be automated; production deployment, irreversible data changes, and external commitments require explicit gates.

The knowledge layer should begin as institutional memory, not as a premature vector database. Decisions, architecture, patterns, failures, customer insights, prompts, tests, and postmortems should be durable, searchable artifacts. Semantic retrieval and graph relationships can be added after repeated product work produces enough material to justify them.

Self-healing is defined narrowly and honestly as observable, fault-tolerant, automatically recoverable software with bounded autonomous remediation. The correct flow is detect, classify, contain, retry or degrade, alert, diagnose, propose remediation, verify with tests, pass a policy gate, deploy, and verify again. The system must never give an AI agent unlimited authority over production.

## What this phase takes from the context

This phase adopts the product-foundry framing, the trust-layer invariant, the repository-as-source-of-truth rule, the lifecycle artifact model, and the bounded-autonomy rule. It does not add unrestricted agents or a RAG system yet. Those would create architecture before enough real product evidence exists. The durable job system is now the spine onto which research, product, design, engineering, QA, deployment, and knowledge adapters can be added one at a time.

## Capability after this phase

A founder can create an opportunity, turn it into a product brief, generate an implementation plan, prepare an isolated repository branch, apply explicit file changes, run the repository's verification command, create a preview from verified build output, and attach the evidence to the durable job. Every step is auditable and tenant-scoped.

The next compounding layer is a knowledge index over these artifacts. It should retrieve prior decisions, patterns, failures, and verification evidence into future briefs and plans. That layer should be built from actual shipped work rather than from a large collection of speculative documents.
