# Task document format

The task document is the single input to the unattended loop: one markdown file, written by a
human or generated by a planner, that says what to build, how to prove it was built, and how the
work divides into independently committable units.

```bash
npm run factory:run -- --repo /path/to/target --task /path/to/task.md
```

It is markdown so a person can write it, read it, and execute every step of it by hand. It is
parsed strictly so the loop can refuse anything ambiguous instead of guessing what the author
meant. Nothing in this file is advisory: each rule below maps to a refusal the parser makes
today (`src/services/taskDocumentService.ts`).

## Shape

```markdown
# Task: Ship the audit page

## Goal
Give an operator a page that shows what the factory committed today.

## Constraints
- No new runtime dependencies
- Every claim on the page must come from git

## Models
models.implementer: local/qwen2.5-coder:14b

## Verification
npm run verify

## Milestones
### M1: Audit route
type: fix
independent: true
split: criterion
verify: node check-route.cjs
- [ ] the route file exists
  - check: node -e "require('fs').accessSync('src/audit.ts')"
- [ ] the route is exported
  - check: node -e "process.exit(0)"
### M2: Audit UI
depends: M1
- [ ] the page renders without throwing
```

## Sections

| Section | Required | Contents |
|---|---|---|
| `# Task: <title>` | yes | Exactly one top-level heading, and it must begin `Task:`. |
| `## Goal` | yes | Free text: what the finished work is for. |
| `## Constraints` | no | List items (`- …`) only. Each becomes a line in the implementer's prompt. |
| `## Models` | no | One `models.<role>: <providerId>/<model>` per line. |
| `## Verification` | no | One command line: the default verification for every milestone. |
| `## Milestones` | yes | The work, as `### <id>: <title>` headings. |

Any other `##` section, any heading outside `## Milestones`, and any second `#` heading are
refused with the line number that produced them.

## Milestone fields

Each `### <id>: <title>` heading may be followed by field lines before its criteria:

| Field | Default | Meaning |
|---|---|---|
| `type: feat\|fix\|docs\|refactor\|test\|chore` | `feat` | The conventional-commit type of every unit this milestone produces. |
| `independent: true\|false` | `true` | Declares the milestone needs nothing else to start. |
| `depends: M1, M3` | none | Milestones that must be committed first. Unknown ids and cycles are refused. |
| `split: milestone\|criterion` | `milestone` | `milestone` = one unit; `criterion` = one unit per acceptance criterion, run in order. |
| `verify: <command>` | document default | The command that proves this milestone's units. |

Milestone ids must match `[A-Za-z][A-Za-z0-9_-]{0,31}` and be unique.

## Acceptance criteria

```markdown
- [ ] a human-readable statement of what must be true
  - check: <command that exits 0 only when it is true>
```

- Every criterion is a list item with a checkbox. An empty criterion is refused.
- The optional nested `check:` line is matched against the raw line, so its indentation is what
  separates it from the criterion above: two spaces (or a tab) before the `-`.
- A `check:` without a criterion, an empty `check:`, or a second `check:` on one criterion is
  refused.

A criterion's `check` is documentation for the reader and for the model; what the loop actually
executes is the milestone's (or document's) `verify` command. Both are run as commands and
neither is ever replaced by a model's account of the result.

## From document to work units

`decompose()` turns the document into the units the loop runs:

- `split: milestone` → one unit per milestone.
- `split: criterion` → one unit per criterion, each depending on the previous one.
- Cross-milestone `depends:` edges are lifted onto the units a milestone produced, so a STUCK
  dependency stops dependent work instead of running past it.
- A milestone declaring more acceptance criteria than `doctrine/loop.json` →
  `unit.maxAcceptanceCriteriaPerMilestone` (5) is refused at parse time. That cap is what makes
  "small, independently mergeable commits" a property of the input rather than a hope about the
  output.

Every unit carries `id`, `milestoneId`, `title`, `type`, `criteria`, `dependsOn`, and `verify`.
Dependency cycles and unknown dependency ids are refused before any work starts.

## Model assignment

The `## Models` section overrides doctrine per role:

```
models.implementer: stub/stub-code
```

- The value must be `<providerId>/<model>` with a lowercase provider id, or the document is
  refused.
- Precedence: `FACTORY_MODEL_<ROLE>` → `FACTORY_MODEL_TIER_<TIER>` → the task document →
  `doctrine/agents/models.json`.
- Every declared role must resolve to a well-formed assignment; only the roles the loop actually
  calls must have a registered provider for the tenant.

## Verification resolution

For each unit, in order:

1. the milestone's `verify:` line,
2. else the document's `## Verification` line,
3. else the repository's own profile (`src/services/verificationProfileService.ts`).

If none of the three yields a command, `plan-is-executable` refuses the run: a unit with no way
to be proven is not a unit the loop will attempt.

## Refusals

Every one of these stops the run before any file is written:

| Condition | Code |
|---|---|
| Empty document, second `#` heading, unknown section | `TASK_DOCUMENT_INVALID` |
| Milestone heading not `### <id>: <title>`, duplicate id | `TASK_DOCUMENT_INVALID` |
| Milestone with no acceptance criterion | `TASK_DOCUMENT_INVALID` |
| Dependency on an unknown milestone, or a cycle | `TASK_DOCUMENT_INVALID` |
| Too many criteria for one milestone | `TASK_DOCUMENT_INVALID` |
| Field line with an unrecognised key or value | `TASK_DOCUMENT_INVALID` |
| `models.<role>` not `<providerId>/<model>` | `TASK_DOCUMENT_INVALID` |
| More than one command in `## Verification` | `TASK_DOCUMENT_INVALID` |
| The task file does not exist | `TASK_DOCUMENT_NOT_FOUND` |

## Dual mode

Nothing here requires the loop. A person can:

```bash
# read the plan the loop will follow
npx tsx -e "const {loadTaskDocument,decompose}=await import('./src/services/taskDocumentService'); \
  const d=loadTaskDocument('task.md'); \
  console.log(decompose(d,{maxAcceptanceCriteriaPerMilestone:5}).map(u=>u.id).join('\n'))"
```

and then make each change, run each `verify` command, and commit each unit by hand, in the same
order, with the same gates described in `doctrine/DOCTRINE.md`.
